# Workflow Rules

Paths are workspace-relative. `<plugin>` is the installed plugin directory (`${CLAUDE_PLUGIN_ROOT}` inside skills). Pass `--workspace .` (or set `JOBSEARCH_WORKSPACE`) to every script.

**Before analyzing a JD:**
1. Run `python3 <plugin>/scripts/tracker_query.py match "<Company>" --role "<role keywords>"`. It fuzzy-matches the company (legal suffixes and parenthetical sub-brands are ignored) across the live tracker and any `tracker.archives` without loading them into context. Read an archive by hand only if the script fails.
2. If the **same company + same role** exists: show the existing entry (status, match %, date, outcome) and ask whether to re-analyze, update the existing entry, or skip.
3. If the **same company but a different role** exists: show all previous entries for that company (status, role, date, outcome) and flag relevant signals ("rejected for Role X on DATE", "active application for Role Y"). Then analyze, noting the history.
4. If the company is not in the tracker: proceed normally.
5. **Never auto-skip a new role because the company has a prior `SKIP`, `REJECTED` or `WITHDRAWN` entry.** Surface the history, then analyze the new role on its own merits.

**After a JD analysis:**
1. Run the liveness gate, then score with the **JD Fit Scoring Rubric** (`docs/scoring-rubric.md`): weighted dimensions plus pass/fail gates. Do not eyeball Match %. Write `**Overall Score: NN** - <Verdict>` into `analysis.md`.
2. Create the company folder (`paths.output_dir_pattern`) and save the analysis as `analysis.md`. Also save the full posting text verbatim (never a summary) as `job-posting.md`: postings expire, and interview prep and follow-ups need the exact text that was applied to. If the text is no longer available, write nothing and say so; never reconstruct a posting from memory.
3. Add or update the tracker row: Status `To Apply` (verdict Apply or Apply with caveats) or `SKIP` (Skip, failed gate, closed posting). For Discuss (Moderate Fit) add no row until the user decides. Populate Company, Role, Source, Match % (= Overall Score), Salary, Folder, Updated.
4. Update `pipeline.md` notes if there are blockers or signals worth tracking.
5. Suggest CV tailoring if the verdict is Apply or Apply with caveats. Do not suggest a cover letter.

**After CV tailoring:**
- Build from `<folder>/spec.json` with `python3 <plugin>/scripts/build_application.py <folder> --cv --verify` (see `docs/build-application.md`); do not create per-company scripts.
- Run the **Draft Review Pass** (`docs/cv-letter-quality.md`) BEFORE the user sees the draft (one review, one revision), then present a single package for one approval; apply the CV Trimming Rule if the CV exceeds the page limit.
- Before moving the role to `APPLYING`, do the warm-path check (Referral-First Sourcing Rule 1).
- Output lands in the company folder, named by `identity.output_name_pattern`; a second role at the same company uses a role-specific `file_name`. PDFs are generated by the builder (LibreOffice required).
- **Verify mechanically before presenting** (a visual read misses all of these): `build_application.py --verify` runs `verify_pdf.py` (ATS text layer, page count, ASCII date hyphens, base-CV email, required keywords; exit 1 = problem) and `verify_layout.py` (holes, early page ends, stranded headings; exit 2 = no extractor, not a verdict). Date ranges in role and education lines use an ASCII hyphen (`July 2023 - October 2024`); an en dash joined to a year can make an ATS drop the date.
- Present a keyword coverage table from the extracted text: `covered` / `synonym-only` (switch to the posting's exact term if truthful) / `missing (have it)` (add to an experience bullet) / `missing (gap)` (leave it, address honestly). A phrase reported missing may be an extractor spacing artifact: re-check with `pdftotext -layout -enc UTF-8` before concluding.
- Update the tracker: Status `APPLYING`.

**After application submitted:**
- Tracker: Status `APPLIED`, `Applied` column = submission date (YYYY-MM-DD).

**After rejection at any active stage (SCREENING or INTERVIEW -> REJECTED):**
- Tracker: Status `REJECTED`, `Offer / Rejected` column = rejection date.
- Draft a short, professional feedback-request message (2-3 sentences, warm), tailored to the stage, and save it as `<folder>/feedback-request.md`:
  - **After an HR/screening call:** thank them briefly, ask what profile or criteria did not match, and whether other roles could fit better.
  - **After a technical or competency interview:** thank them for the process and ask what could be improved or what was the deciding factor.
- **If feedback is received** (the user pastes it in):
  1. Identify concrete skill gaps, weak areas or mismatches.
  2. Check the knowledge base: if the gap is already documented, mark it a confirmed weak point to prioritize.
  3. If it is new and relevant (technical skill, domain knowledge, interview format), add it to the knowledge base's gaps section with topic, source company, date and suggested action.
  4. Add a signal line to `pipeline.md` (company, stage, gap topic) for weekly review.
  5. Summarize the gap and suggest 1-2 concrete next steps (resources, practice areas, topics for interview prep).

**After cover letter:**
- Build from the `letter` section of `<folder>/spec.json`: `build_application.py <folder> --letter --verify`.
- Run the Draft Review Pass before presenting.
- Output: `.docx` and `.pdf` in the company folder. The verification covers one page and layout.
- If the portal has free-text fields (self-introduction, project entries, a pitch under a character limit, a motivation question), offer to draft them per `application-forms.md`. Required fields are drafted even when no cover letter was requested.

**When preparing for an interview (interview-prep skill triggered):**
1. **Always read `interview-kb-hard-skills.md` and `interview-kb-soft-skills.md` first.** They are the base layer. Do not ask the user for information already documented there.
2. Use the KB files as the foundation. The company-specific `<folder>/interview-prep.md` adds only: company research (culture, stack, interview format), the story-to-JD mapping (which STAR story leads per question), role-specific technical focus areas, gap response scripts, and questions to ask.
3. Save the generated prep as `<folder>/interview-prep.md` (optionally a drill book via the interview-drillbook skill).
4. **After an interview** (the user reports back): add new technical questions to `interview-kb-hard-skills.md`, new behavioral questions to `interview-kb-soft-skills.md`; if a gap was revealed, update the Known Gaps table (topic, source company, date, priority, suggested action) and the knowledge base's gaps section.
5. **Never generate a company-specific prep from scratch** without reading the KB files. The KB prevents duplication and flags confirmed gaps automatically.
6. **Consistency brief (every pack).** List the claims on the submitted CV and letter that the interviewer is most likely to probe. No claim in the room that is not on paper, and every claim on paper must be defensible in depth.
7. **Stage-specific packs.** From the second round on, one file per stage (`interview-prep-<stage>.md`); earlier packs stay as history. Order likely questions by: feedback recorded from earlier stages, then JD-analysis gaps (honest bridge: acknowledge, adjacent experience, learning path; never invent experience), then the posting's requirements, then the stage type. "Why this company" uses only verified hooks from the company research cache.
8. **Mock interview and thank-you.** Offer a mock round after the pack (warm-up, role-specific technical, 1-2 behavioral questions tied to the posting, one curveball; short feedback after each answer, naming the better STAR story). After any completed stage, offer a 2-3 sentence thank-you note in the Humanize voice, with no claims beyond the submitted materials.

**Whenever status changes** (recruiter reply, interview scheduled, rejection, offer):
- Update the tracker row: Status, stage column date, Next Action, Updated.
- After any data change run `restyle_tracker.py` (restyles and verifies in one pass).

**When rebuilding the tracker from scratch** (for example after a schema change):
- Follow `docs/tracker-schema.md`, regenerate with openpyxl, source data from the existing rows (never lose entries), back up first, then run `restyle_tracker.py`.
